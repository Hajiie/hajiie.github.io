# Linker: 비개발자용 서버 및 환경 관리 앱

## 배경

- 2026년 초, 연구실에 있는 서버 컴퓨터에 원격으로 접속하여 사용하던 중 비개발자인 다른 연구원들이 사용을 힘들어하여 제작

## 주요 기술 및 구현
Framework
- **Electron** 을 사용하여 크로스 플랫폼 데스크톱 앱(Vite 기반)을 구성

Frontend Framework
- React 및 Tailwind CSS를 사용하여 Lucide 아이콘 기반의 반응형 UI 제작

Backend Framework
- Node.js 를 사용하여 SSH 세션 및 원격 시스템을 제어 수행

Server Communication
- ssh2 모듈로 SSH 연결, SFTP 전송 및 포트 포워딩 구현
- xterm.js와 node-pty를 사용하여 로컬 및 SSH 터미널 구성

Database
- lowdb 기반의 JSON DB를 Electron의 `userData`에 저장
- 비밀번호와 개인 키 암호는 운영체제의 `safeStorage`로 암호화하여 저장
- DB 스키마 검증, 순차 저장, 이전 상태 백업과 명시적 복구 절차 적용

## 시스템 주요 기능
서버 관리 (Server Management)
- 직관적인 대시보드: 카드형 UI로 등록된 서버 목록을 한눈에 확인.
- 서버 이름, 주소, 포트, 사용자와 Conda 실행 경로 등록·편집·삭제.
- 비밀번호, 개인 키 파일, SSH agent 인증 지원.
- 첫 연결에서 SSH 호스트 키 지문을 확인하고, 저장한 키와 다르면 연결을 거부.
- 서버 설정을 바꾸기 전 기존 작업과 세션을 정리하고, 변경 후 동기화는 일시정지 상태로 유지.

Conda 가상환경 제어 (Conda Environment)
- 환경 리스트: 서버에 설치된 모든 가상환경 자동 스캔 및 시각화.
- 원클릭 생성/삭제: Python 버전을 선택하여 새 환경을 구축하거나 불필요한 환경 제거.
- 같은 이름의 환경을 구분할 수 있도록 전체 경로(prefix)를 함께 표시하고, 기존 환경 작업은 해당 경로를 기준으로 수행.
- 주피터 자동 연결: 선택한 환경에 설치된 Jupyter Notebook을 실행하고 인증 토큰을 유지한 SSH 터널로 기본 브라우저에 연결.
- 로컬·원격 포트를 동적으로 할당하고, 앱에서 실행한 세션만 목록으로 관리하여 개별 종료.

패키지 매니저 (Package Management)
- 설치 목록 확인: 각 환경별 설치된 패키지 명칭, 버전, 설치 채널(Conda/PyPI) 표시.
- 통합 검색 및 설치 
  - Conda Search: Conda 리포지토리에서 패키지 검색 후 즉시 설치. 
  - Pip Direct: 패키지명을 직접 입력하여 PyPI를 통해 설치.
- 안전한 삭제: 휴지통 아이콘 클릭만으로 conda remove 또는 pip uninstall 자동 실행.

SFTP 파일 매니저 (SFTP File Browser)
- 직관적인 탐색: 원격 서버의 디렉토리 구조를 시각적으로 탐색하고 경로 이동 지원.
- 네이티브 드래그 앤 드롭
  - 업로드: 로컬의 파일 및 폴더를 브라우저로 드래그하여 서버에 전송.
  - 다운로드: 서버의 파일 및 폴더를 로컬 폴더로 드래그하여 즉시 다운로드.
- 재귀적 전송: 폴더 구조 전체를 유지하며 재귀적으로 업로드/다운로드 수행.
- 파일별 진행 바이트와 완료 파일 수 표시, 이름 변경·속성 확인·확인 후 삭제 지원.
- 기존 파일 교체는 원격 임시 파일 전송 후 원자적 rename으로 처리. 서버가 원자적 교체를 지원하지 않으면 기존 파일 덮어쓰기를 거부.

터미널 (Terminal)
- 로컬 셸과 SSH 터미널을 앱 안에서 사용하고, 화면 크기에 맞춰 터미널 크기를 조절.
- 창 종료와 서버 설정 변경 시 해당 세션과 PTY 리소스를 정리.

파일 동기화 (Sync)
- 로컬 폴더와 원격 폴더를 연결하고, 시작 시 양쪽 파일을 먼저 병합.
- 초기 병합 이후에는 로컬의 파일 변경·삭제를 서버에 반영.
- 오류가 발생하면 감시와 대기 작업을 중단하고, 수동 재시도 시 현재 폴더 상태부터 다시 비교.

작업 관리 (Operations)
- 업로드·다운로드와 Conda 환경·패키지 변경의 진행 상태, 취소, 명시적 재시도 제공.
- 화면을 이동해도 작업은 메인 프로세스에서 유지.
- 최근 작업 상태와 오류 코드 등을 진단 JSON으로 내보내기. 서버 주소, 파일 경로, 비밀번호, 개인 키와 Jupyter 토큰은 내보내기 대상에서 제외.

반응형 UI/UX (Responsive Design)
- 창 크기에 따라 카드 배열, 모달 여백, 폰트 크기를 조절.
- 작업 진행 상태와 성공·실패 여부를 화면에 표시.

## 동기화와 복구 방식

### 초기 병합과 실시간 반영

| 파일 상태 | 처리 |
| --- | --- |
| 로컬에만 존재 | 서버로 업로드 |
| 서버에만 존재 | 로컬로 다운로드 |
| 양쪽에 존재하고 서버 수정 시간이 더 최신 | 서버 내용을 로컬에 반영 |
| 로컬이 더 최신이거나 수정 시간이 같고 크기가 다름 | 로컬 내용을 서버에 반영 |
| 수정 시간과 크기가 모두 같음 | SHA-256으로 비교하고, 내용이 다르면 로컬 기준 반영 |

초기 병합에서는 파일을 삭제하지 않으며, 수정 시간 비교는 두 컴퓨터의 시계가 맞는 것을 전제로 함.
초기 병합 이후의 감시는 **로컬 → 서버** 방향으로 동작. 서버의 변경을 계속 감시하는 양방향 동기화는 현재 구현 범위에 포함되지 않음.

빈 폴더와 숨김 파일을 포함하되 `.git`, `node_modules`, `.linker-*` 임시 파일은 제외.
겹치는 동기화 루트, 심볼릭 링크와 파일·폴더 타입 충돌을 검사하고, 전송·삭제 직전에 경로를 다시 확인.

### 취소와 재시작

- 파일 전송 취소는 현재 파일을 반영한 뒤 다음 파일부터 중단. 완료한 파일을 되돌리거나 중간 바이트부터 이어받는 방식은 아님.
- 환경·패키지 변경 취소는 앱에서 시작한 원격 프로세스 그룹의 종료를 요청하고 확인. 이미 적용된 설치·삭제는 되돌리지 않음.
- 원격 이름 변경·삭제·파일 교체의 응답이 유실되면 적용 여부를 알 수 없으므로, 이전 요청을 자동으로 재실행하지 않고 새 파일 목록과 상태를 확인하도록 처리.
- 동기화 쓰기를 시작하기 전에 재시작 차단 상태를 DB에 저장. 비정상 종료 후에는 자동 재개하지 않으며 사용자가 상태를 검토한 뒤 명시적으로 재개.
- 중단 중 로컬에서 지운 파일이 서버에 남아 있다면, 다음 초기 병합에서 로컬로 복원될 수 있으므로 재개 전 양쪽 상태 확인이 필요.

### 검증과 현재 배포 범위

타입 검사·회귀 테스트와 별도로, 폐기용 OpenSSH/SFTP·Conda·Notebook 환경에서 실제 전송·인증·종료·장애 복구를 검사.
부분 전송 중 강제 종료뿐 아니라 원격 파일 교체 또는 로컬 최종 rename 직후 강제 종료한 경우에도, 다음 실행에서 자동 재개가 차단되는지와 새 원격 변경이 다시 병합되는지를 확인.
이 조건의 검증이 실제 전원 차단이나 모든 파일시스템의 내구성을 보장하는 것은 아님.

2026년 11월부터 Linker의 빌드·검증은 로컬에서 수행. 현재 macOS ARM64의 서명 없는 DMG/ZIP과 같은 버전 재설치 시 데이터 보존을 확인했으며, Windows·Linux의 새 로컬 배포 절차와 코드 서명·공증은 추가 검증이 필요.

## 프로젝트 의의
비개발자를 위한 편의성 시스템
- 기존 SSH를 통해 컴퓨터를 원격으로 관리하던 프로그램에 비해 직관적이고 아이콘 기반으로 한 가시성 향상
- 복잡한 명령어 기반이 아닌 검색 후 설치, 가상환경 생성 등을 버튼으로 제어

# Linker 트러블슈팅 정리

1~8번은 초기 개발 당시의 문제와 해결 과정이며, 이후 파일 전송·DB·세션 관리는 위의 작업 관리와 복구 방식으로 확장됨.

## 1. Electron Error: Module did not self-register (sshcrypto.node)
문제 및 원인
- `ssh2` 라이브러리의 네이티브 모듈이 번들러에 의해 잘못 처리됨.

해결 방법
- `vite.config.ts`에서 `ssh2` 관련 모듈을 명시적으로 `external` 처리하고, 소스 코드에서 `require` 문법을 사용하여 번들링을 방지함.

## 2. SSH Command Error: conda: command not found
문제 및 원인
- SSH `exec`을 통해 명령어를 실행할 때, 로그인 셸이 아니므로 `.bashrc`나 `.profile`에 정의된 `conda` 경로가 로드되지 않음. 이로 인해 `conda` 명령어를 인식하지 못하는 현상이 발생함.

해결 방법
- 명령어를 실행할 때 `bash -l -c` (로그인 셸) 옵션을 사용하여 사용자 환경 설정을 강제로 로드한 뒤 실행하거나, 환경 설정 파일을 직접 `source` 하도록 명령어를 수정함.

## 3. UI Layout Breakdown on Small Window Sizes
문제 및 원인
- 고정된 패딩과 최소 높이(`min-h`) 설정으로 인해 창 크기가 작아질 때 모달 콘텐츠가 겹치거나 화면 밖으로 나가는 현상이 발생함. 

해결 방법
- Tailwind CSS의 반응형 접두사(`md:`, `lg:`)를 사용하여 화면 크기에 따라 여백과 폰트 크기를 동적으로 조절하고, 모달 내부의 고정 높이 제한을 제거하여 콘텐츠가 유연하게 배치되도록 수정함.

## 4. "Create New Environment" Button Accessibility
문제 및 원인
- 가상환경 리스트가 길어지거나 창 높이가 낮아질 때, 리스트 하단에 고정된 "새 환경 만들기" 버튼이 화면 하단에 가려져 클릭할 수 없는 문제가 발생함.

해결 방법
- 버튼을 스크롤 가능한 컨테이너 내부 하단으로 이동시키고 영역의 `min-h`를 제거하여, 항목이 많아지더라도 스크롤을 통해 항상 버튼에 접근할 수 있도록 구조를 개선함.

## 5. SFTP Drag-Out: Local File Requirement for startDrag
문제 및 원인
- Electron의 `startDrag` API는 로컬에 존재하는 파일 경로를 필수로 요구함. 하지만 SFTP 브라우저에서 드래그를 시작할 때 파일은 원격 서버에만 존재하므로 즉시 드래그를 시작할 수 없음.

해결 방법
- `ipcMain.on`에서 드래그 요청을 받으면, 먼저 서버에서 파일을 로컬 임시 디렉토리(`os.tmpdir()`)로 다운로드함. 다운로드가 완료된 시점에 `event.sender.startDrag`를 호출하여 로컬 경로와 아이콘을 전달함으로써 원격 파일의 드래그 앤 드롭을 구현함.

## 6. SFTP Folder Upload: Recognition Issue
문제 및 원인
- SFTP 브라우저에 폴더를 드롭했을 때, 기존 `sftp.put()` 메서드는 단일 파일만 처리할 수 있어 폴더 구조가 정상적으로 업로드되지 않거나 에러가 발생함.

해결 방법
- 초기 구현에서는 메인 프로세스에서 폴더 여부를 확인하고 `sftp.uploadDir()`로 재귀 업로드하도록 개선함.
- 현재 전송은 파일별 진행 상태와 원자적 교체, 파일 경계 취소를 함께 관리하도록 확장됨.

## 7. SFTP Folder Download: Recursive Support
문제 및 원인
- 원격 서버의 폴더를 로컬로 드래그하여 다운로드할 때, 단일 파일 전용인 `sftp.get()`을 사용하여 폴더 구조가 누락되거나 에러가 발생함.

해결 방법
- `downloadFile` 로직에 `sftp.stat()`을 추가하여 원격 경로가 폴더인지 확인하고, 폴더일 경우 `sftp.downloadDir()`을 사용하여 하위 디렉토리와 파일을 모두 재귀적으로 다운로드하도록 수정함.

## 8. SFTP Drag-Out: macOS Icon Path Crash
문제 및 원인
- macOS(darwin) 환경에서 Electron의 `startDrag` API 호출 시 전달된 `icon` 경로에 실제 이미지 파일이 존재하지 않으면 앱이 즉시 크래시되거나 드래그가 시작되지 않는 현상이 발생함.

해결 방법
- 프로젝트 내에 기본 아이콘이 없는 경우를 대비해, 드래그 시작 시점에 1x1 크기의 투명 PNG 데이터를 Buffer로 생성하여 임시 폴더에 저장함. 해당 임시 파일 경로를 아이콘으로 사용함으로써 아이콘 부재로 인한 크래시를 방지함.

## 9. Jupyter 포트 충돌과 원격 프로세스 정리

문제 및 원인
- 고정 포트가 이미 사용 중이거나, 실행 요청을 취소한 뒤 늦게 도착한 준비 응답으로 세션이 남을 수 있음.
- SSH 연결이 끊겼다는 사실만으로 원격 Notebook이 종료되었다고 판단할 수 없음.

해결 방법
- 로컬·원격 포트를 동적으로 할당하고, 인증된 HTTP 응답과 SSH 포워딩을 확인한 후 브라우저를 실행.
- 세션별 감독 프로세스를 두고 종료 API와 앱 소유 프로세스 그룹의 종료 결과를 확인.
- 종료 확인에 실패하면 성공으로 표시하지 않고 오류 상태를 유지.

## 10. SFTP 응답 유실과 동기화 재시작

문제 및 원인
- 서버가 파일을 교체하거나 삭제한 뒤 응답만 유실되면, 클라이언트의 오류와 실제 파일 상태가 일치하지 않을 수 있음.
- 앱 강제 종료 후 예전 작업을 그대로 반복하면 이미 완료한 변경을 다시 실행할 수 있음.

해결 방법
- SFTP 요청별 대기 기한을 적용하고, 변경 적용 여부가 불확실한 오류를 별도로 구분.
- 건강한 SSH·터미널 채널을 유지하면서 실패한 SFTP 작업을 중단하고, 기존 요청의 자동 재실행을 차단.
- DB의 재시작 차단 상태와 명시적 확인 절차를 사용하고, 재개 시에는 양쪽 폴더를 새로 비교.
- 강제 종료와 응답 유실을 주입하여 대상 원본·완료 파일·아직 처리하지 않은 파일의 상태를 각각 검사.

## 11. DB 손상 시 설정이 초기화되는 문제

문제 및 원인
- 저장 중 오류나 손상된 DB를 빈 설정으로 취급하면 기존 서버와 동기화 설정을 잃을 수 있음.

해결 방법
- 스키마를 검증하고 임시 파일·이전 상태 백업·원자적 교체를 사용하여 DB 변경을 순차 저장.
- DB가 손상되면 자동 초기화 대신 복구 창에서 검증된 백업 복구 또는 초기화를 명시적으로 선택.
- 복구 전 원본을 보존하고, 복구된 동기화 연결은 일시정지 상태로 시작.
